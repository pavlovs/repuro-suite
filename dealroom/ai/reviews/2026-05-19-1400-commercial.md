# Codex Review: DR-GC Golden Corpus Generator Specs

Scope: `commercial`  
Target set: `SPEC-MODEL.md`, `SPEC-ONEPAGER.md`, `SPEC-OFFER.md`, `SPEC-LOI.md`, `SPEC-NDA.md`, `SPEC-RFI.md`

Basis for this review:
- The six spec files in `dealroom/ai/golden-spec/`
- `dealroom/config/golden/manifest.json`
- `dealroom/src/generate/rfi.py`
- `dealroom/tools/susa_to_model.py`

Findings are ordered by severity.

## Findings

1. **Critical: `SPEC-MODEL` gives mutually incompatible write boundaries for `Bewertung`, which is the highest-risk workbook surface.**  
   The spec says `Bewertung` is read-only / formula-driven (`SPEC-MODEL.md:55`, `SPEC-MODEL.md:343-345`, `SPEC-MODEL.md:367`, `SPEC-MODEL.md:546`), but the same spec later lists `L10-L12` and `L16-L19` as cells Roman manually sets (`SPEC-MODEL.md:378-379`). Those rows are already defined as formula outputs. A generator built from this spec can reasonably conclude that overwriting `Bewertung` outputs is allowed.  
   Required fix: remove formula-output cells from the manual-write map and name the actual driver cells Roman sets (targets, multiples, leakage inputs) instead.

2. **High: `SPEC-MODEL` hardens the wrong multi-entity rule.**  
   The sheet architecture and edge-case sections correctly document that FOX keeps entity detail inside `GuV-Konten` columns, not separate sheets (`SPEC-MODEL.md:80`, `SPEC-MODEL.md:398-402`). Hard Constraint 9 then states that multi-entity models follow a sheet-per-entity pattern (`SPEC-MODEL.md:558`). That is false for one of the four cited golden models.  
   Risk: an agent or reviewer may reject valid FOX structure or try to “normalize” it.  
   Required fix: rewrite the rule as “preserve the native consolidation pattern of the chosen golden model.”

3. **High: `SPEC-OFFER` still has no single canonical input contract.**  
   The fill map uses names that do not exist in the schema or use a different shape: `company_name`, `seller_salutation_name(s)`, `street`, `plz_city`, `payment_trigger_year` (`SPEC-OFFER.md:107-115`). The schema instead defines nested `sellers[]` fields, `pricing.earn_out_payment_year`, and `pricing.sofortzahlung_gross` (`SPEC-OFFER.md:204-239`). The workflow also uses `seller_count` without defining it anywhere (`SPEC-OFFER.md:597`).  
   Risk: header/salutation/pricing code will drift into ad hoc adapters and silent mapping bugs.  
   Required fix: publish one authoritative schema and reuse the exact field names in fill map, workflow, and validation rules.

4. **High: `SPEC-LOI` cannot represent all earn-out variants it claims to cover, and its validation references an undefined total consideration field.**  
   Clause D is described as handling table structure plus multiplier/base EBIT logic (`SPEC-LOI.md:63`), and the edge cases reference both compact and granular bracket/formula variants (`SPEC-LOI.md:188-193`). But the schema only provides `earn_out_table`, `adjustment_multiplier`, and `base_ebit` (`SPEC-LOI.md:106-116`) and never defines `earn_out_type`, floor/cap/minimum fields, or `total_consideration`. The workflow then validates `pricing.sofortzahlung + pricing.earn_out_max = total consideration` (`SPEC-LOI.md:271`).  
   Risk: implementers will invent missing fields or silently collapse distinct commercial patterns into one path.  
   Required fix: either narrow LOI scope to the actually observed variant set or add the missing canonical earn-out fields.

5. **Medium-High: `SPEC-LOI` violates the “golden evidence only” standard in its wildcard hardening section and still leaves the template path unresolved.**  
   Section C includes explicitly hypothetical variants such as `Immobilie` and `Uebergangsfinanzierung` (`SPEC-LOI.md:173-174`). That is not golden-corpus evidence; it is brainstorming inside the spec. The template registry also still contains `[ROMAN: confirm ...]` instead of a concrete path (`SPEC-LOI.md:341`), even though the manifest already records the file (`manifest.json:198-205`).  
   Risk: the generator boundary for the least-templatable clause becomes broader and less traceable than the corpus supports.  
   Required fix: remove hypothetical examples from normative logic and replace the placeholder path with the manifest-backed golden path.

6. **Medium: `SPEC-ONEPAGER` has an unsafe fallback when no Q2 chart is available.**  
   Edge-case rule 9.2 says the Q2 area must be left empty and flagged if no chart is provided (`SPEC-ONEPAGER.md:431`). The later think-cell section and workflow allow reusing the previous deal’s chart or leaving `TO BE UPDATED` placeholders in place (`SPEC-ONEPAGER.md:498`, `SPEC-ONEPAGER.md:563`). The same spec also treats yellow editorial markers as must-remove and calls out confidentiality explicitly (`SPEC-ONEPAGER.md:468`, `SPEC-ONEPAGER.md:587`).  
   Risk: a deck can ship with another deal’s financial visual still embedded.  
   Required fix: make the empty-state rule absolute for external output. Do not permit prior-deal chart carryover.

7. **Medium: `SPEC-NDA` is not build-ready as a generator spec yet.**  
   The spec depends on a cleaned bilateral template that does not exist yet (`SPEC-NDA.md:204`) and on Roman confirming that bilateral is the only target-side variant (`SPEC-NDA.md:195`, `SPEC-NDA.md:210`). It also stores the future template under `dealroom/templates/` instead of the golden-corpus location used elsewhere (`SPEC-NDA.md:124`, `SPEC-NDA.md:214`). Compared with the other specs, it has no explicit anti-pattern section and no generation workflow with a Roman review gate.  
   Risk: the simplest generator bypasses the same copy/review discipline imposed everywhere else.  
   Required fix: create and register the bilateral template under `dealroom/config/golden/nda/`, add a short generation workflow, and add the applicable anti-patterns.

8. **Medium: `SPEC-RFI` says Roman reviews every RFI before sending, but the workflow has no human gate and anti-pattern handling is only a cross-reference.**  
   Stage 4 writes `deal_questions` and emits PDF/XLSX directly (`SPEC-RFI.md:176-179`), while the confidence section explicitly says low-confidence creative questions still require Roman review (`SPEC-RFI.md:345`). Anti-patterns are only linked in Cross-References, not scoped into actionable generator rules (`SPEC-RFI.md:388`).  
   Risk: low-confidence or confidential questions become operational output without an explicit approval boundary.  
   Required fix: add a review gate between refinement and output, and inline the applicable anti-patterns (`CONFIDENTIAL-LEAK`, no fabrication of facts, no overwrite of sent questions).

## Cross-Spec Consistency

- **Shared identity fields are not canonical.**  
  `codename` / `legal_name` are used in Onepager, Offer, and LOI (`SPEC-ONEPAGER.md:284-306`, `SPEC-OFFER.md:183-239`, `SPEC-LOI.md:81-129`), while RFI uses DB-facing `code_name` / `company_name` (`SPEC-RFI.md:107-115`) and NDA uses isolated `target_company_name` (`SPEC-NDA.md:69-83`).

- **Shared pricing concepts are modeled differently by document instead of being mapped from one canonical shape.**  
  Onepager uses `valuation.*` in `M EUR` floats (`SPEC-ONEPAGER.md:297-304`), Offer uses `pricing.*` in `EUR` ints (`SPEC-OFFER.md:212-239`), and LOI uses a smaller `pricing.*` subset (`SPEC-LOI.md:106-116`). The same commercial facts are therefore renamed and re-unitized per spec.

- **Template storage discipline is inconsistent.**  
  Offer and Onepager point to `dealroom/config/golden/...`, LOI leaves a placeholder path, and NDA proposes `dealroom/templates/`. This should be one rule across the suite.

## Missing Risks Not Fully Covered

- **Live-vs-golden drift on working files:** Offer handles prior-version continuity well, but the same “read latest working file before edit” discipline is not surfaced equally clearly in LOI/NDA.
- **Canonical unit conversions across generators:** Onepager consumes `M EUR`, Offer/LOI consume `EUR`, Model mixes `EUR` and `K EUR`. The suite needs one explicit upstream conversion contract.
- **Spec-to-spec reuse boundary for management-transition data:** Offer, LOI, Onepager, and RFI all consume seller/GF transition information, but there is no shared schema for it. This will create duplicated mapping logic.

## Bottom Line

The strongest specs are `SPEC-MODEL`, `SPEC-ONEPAGER`, and `SPEC-OFFER`; they are evidence-rich and operationally close. The main blockers are:

1. `SPEC-MODEL` write-boundary contradiction on `Bewertung`
2. `SPEC-LOI` incomplete commercial schema + unresolved template path
3. `SPEC-NDA` missing concrete template/governance layer
4. `SPEC-RFI` missing explicit approval gate

I would not treat the six-spec set as generator-ready until those four items are closed.
