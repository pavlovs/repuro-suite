# Cockpit UX Review — Linear & Notion Benchmark

**Date:** 2026-06-16
**Method:** Reverse-engineered Linear.app and Notion UX patterns via public docs, design articles, and feature pages. Compared against live cockpit (screenshots from e2e review + codebase audit of static/js/*.jsx, cockpit.css, boot.js, db.py, api.py).

---

## 1. Current State Summary

The cockpit (M1–M4 done) ships 6 views, 3 workstream sub-layouts, Ctrl+K search, task drawer, quick-add, board drag-drop, undo, agent queue, timeline, relations graph, meeting mode, and 3 density modes. For a tool built in a week, this is a strong foundation.

**Domain-specific differentiators (keep and enhance):**
- Prerequisite readiness coloring (green/amber/red computed from dependency chain)
- Waiting-on / chase model (who has the ball, since when, next chase date)
- Relations dependency graph (visual prereq chains across workstreams)
- Agent queue with human-in-the-loop approval
- Dealroom.db integration (stage mirror, codenames only)

## 2. Architecture Gaps (entity model problems)

### 2.1 No deal as a first-class view

`deal_mirror` holds codename + stage (read-only). Tasks carry `task.deal` (free text). Workstreams carry `deal_codename`. But there is no "Deal page" — you can't click Fox and see all Fox tasks across all workstreams, Fox's waiting items, Fox's blockers, Fox's timeline in one place.

**Linear equivalent:** Project = everything about a deliverable in one view.
**Impact:** Can't prep for a deal call without mentally cross-referencing workstreams + relations + timeline.
**Fix:** Add a Deal view that cross-cuts: `WHERE task.deal = ? OR workstream.deal_codename = ?`. Shows deal stage (from mirror), all tasks grouped by deliverable, waiting items, blockers, progress.

### 2.2 Workstream conflates thematic grouping with deal container

"Fundraising" (thematic, multi-deal) and "Fox — DD" (deal-specific) are both workstreams. A Fox admin task under "Admin" workstream disappears from Fox-filtered views unless separately tagged with `task.deal = Fox`.

**Linear equivalent:** Teams (thematic) vs Projects (goal-bound). Orthogonal axes.
**Impact:** "All Fox tasks" requires knowing which workstreams touch Fox + checking orphan tags.
**Fix:** Enforce `task.deal` on all deal-related tasks regardless of workstream. The Deal view (2.1) aggregates across workstreams by deal codename.

### 2.3 External parties are free text

`waiting_on_party` = "Ebner Stolz", "seller", "ASF", "Kreipel" — unstructured strings. No normalization, no entity to query against.

**Linear equivalent:** Customer entity linked to issues.
**Notion equivalent:** Person/relation properties linking to a contacts database.
**Impact:** Can't answer "all items waiting on Ebner Stolz" without text matching. No party-level summary (N items, avg response time, last chase).
**Fix (lightweight):** A `parties` table (name, type, contact_hint). `waiting_on_party` references by name (or ID). UI: party autocomplete in the waiting modal. Party summary view or chip-click filter.

### 2.4 No activity / comments model

`detail` is a single overwritable text blob. `audit_log` exists in DB but has zero UI. No comments, no conversation thread, no "who changed what when" visible to users.

**Linear equivalent:** Issue comments + activity timeline per issue.
**Notion equivalent:** Page comments + version history.
**Impact:** Two users sharing context via a single text field. Critical gap before Flo onboarding (M5). Agent results have no review conversation.
**Fix:** (a) Surface audit_log in drawer as activity feed (low effort — data exists). (b) Add a `comments` table for structured conversation per task.

### 2.5 Tags exist in schema but not in UI

`tasks.tags` is a JSON array — schema supports it, zero UI. No tag picker, no tag filter, no tag display anywhere.

**Linear equivalent:** Colored, hierarchical labels on every issue. Filterable in all views.
**Notion equivalent:** Multi-select properties with colors.
**Impact:** No cross-cutting classification beyond workstream/deal/owner/status.
**Fix:** Surface tags in drawer (picker), table (pills), and filter bar. Low effort.

### 2.6 Deliverable = container + milestone (overloaded)

"Fundraising partner decision" is simultaneously a task container (holds 4 tasks), a milestone (target date 26/06), and a progress-tracked entity (0/4). Linear separates Projects (containers) from Milestones (checkpoints).

**Impact:** Not broken at current scale. But the mental model is fuzzy — is a deliverable a "what" (goal) or a "where" (bucket)?
**Fix:** Not urgent. Clarify in naming: deliverables are work packages with deadlines. If pure checkpoints are needed later, add a milestone entity.

### 2.7 Prerequisites stored as JSON, not a relation table

`tasks.prereqs` = `[{"ref": "t-5", "hardness": "hard"}]`. Dependency queries require scanning all tasks. Relations view builds graph client-side.

**Impact:** Works at 40 tasks. Doesn't scale. The dependency graph is the cockpit's most unique feature — it deserves a clean backing model.
**Fix:** `prerequisites(task_id, prereq_ref, hardness)` table. Both directions queryable via SQL. Simplifies compute pipeline.

## 3. Interaction Gaps (UX patterns from Linear/Notion)

### P0 — High impact, daily friction

| Gap | Linear pattern | Cockpit state | Effort |
|-----|---------------|---------------|--------|
| **Keyboard navigation** | J/K move, S status, C create, Space peek, ? help, G+X go-to | Only Ctrl+K and Ctrl+Enter | S |
| **Inline editing** | Click any cell to edit status/owner/date/text without opening detail | Status pill clickable; everything else requires drawer | M |
| **Command palette depth** | Cmd+K does actions + navigation + recent: "Set priority high", "Go to Timeline" | Ctrl+K searches tasks only — no commands, no nav | M |
| **Drag reorder in table** | Manual ordering in list view, drag between groups | Board has drag-drop; table has no reordering | S |

### P1 — Medium impact, weekly value

| Gap | Pattern source | Cockpit state | Effort |
|-----|---------------|---------------|--------|
| **Saved views / custom filters** | Notion: unlimited saved views per database. Linear: custom views per team | Fixed views only — can't save "My blocked" or "Fox tasks due this week" | M |
| **Grouping/sorting controls** | Both: group by any property, sort by any property, sub-group | Table groups by workstream→deliverable (fixed). Board: status or workstream only | M |
| **Bulk actions** | Both: multi-select → batch status/assign/priority change | One-at-a-time only | M |
| **Expand drawer to full page** | Linear: side peek → full page. Notion: side/center/full configurable | Drawer only, no full-page option | S |

### P2 — Polish

| Gap | Pattern source | Effort |
|-----|---------------|--------|
| **Activity feed in drawer** (from audit_log) | Linear: issue activity timeline | S (data exists) |
| **Peek preview** (Space bar hover) | Linear: macOS Quicklook-style preview | M |
| **Dark mode** | Both (Linear dark-first, Notion light+dark) | S (CSS vars exist) |
| **"What changed" badges** | Linear: inbox with unread. Notion: page updates | M |
| **Links/attachments in drawer** | Both: inline links, file embeds | S (schema exists) |

## 4. What NOT to Copy

These Linear/Notion patterns don't fit a 2-user M&A deal execution tool:

- **Notion's block editor** — task notes are short context, not documents
- **Notion's database-per-view flexibility** — cockpit's value is opinionated structure
- **Linear's Cycles/Sprints** — M&A work isn't sprint-based; waiting-on/chase is better
- **Linear's label hierarchy** — deal codenames + workstreams already serve this
- **Notion's template gallery** — New Deal playbook is the only template needed
- **Notion's automation triggers** — agent queue is the cockpit's automation layer

---

## 5. Recommended Build Order

**Phase A — Architecture (before M5/Flo onboarding):**
1. Deal view (cross-cutting aggregation by codename) — new view in sidebar
2. Surface audit_log as activity feed in task drawer
3. Party autocomplete for waiting-on (lightweight normalization, no new table required — just deduplicated suggestions from existing data)
4. Surface tags in UI (drawer picker + table pills + filter)

**Phase B — Interaction speed (can interleave with A):**
1. Keyboard shortcuts (J/K, S, C, O, Enter, ?, Esc)
2. Inline editing (text, due, owner clickable in table rows)
3. Command palette actions + navigation mode
4. Grouping/sorting controls in table view

**Phase C — Scale prep (after trial verdict):**
1. Saved views / custom filter tabs
2. Prerequisites relation table (migrate from JSON)
3. Comments table for task conversations
4. "What changed" / personal inbox badges
5. Bulk actions
