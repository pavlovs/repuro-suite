## Verdict
revise — build-time concatenation is a pragmatic fit for your constraints, but the current plan under-specifies dependency safety, validation, and migration guardrails.

## Critical issues
1. **Architecture: Build-Time Concatenation / `JS_LOAD_ORDER`** — Problem: dependency correctness is enforced only by manual file order, which is brittle as modules grow; one new top-level call or `const` function dependency can break at runtime with no preflight signal. Suggested fix: add a lightweight dependency contract per file (for example `// requires: state, helpers`) and a Python preflight that validates required symbols/modules before concatenation; also fail build on unresolved references in declared dependencies.
2. **Phase 1, step 4 (byte-identical diff)** — Problem: byte-identical output is too strict and can create false failures from harmless whitespace/comment changes, while still missing behavioral regressions. Suggested fix: replace with parity checks: placeholder replacement parity, deterministic bundle hash, and scripted smoke checks across all views (serve mode + static export).
3. **Phase ordering (Phase 1 cutover before safety net)** — Problem: the plan switches structure early without an explicit fallback path; if extraction fails midway, dev workflow can stall. Suggested fix: keep dual build paths temporarily (`legacy_single_file` and `concat_mode`) behind a flag until Phase 2 completion and acceptance checks pass.
4. **Phase 3 hot reload** — Problem: rebuilding `_html_content` on file change is underspecified for request-time consistency and caching; concurrent requests can serve mixed states, and browser cache can hide updates. Suggested fix: rebuild to a temp buffer then atomically swap, increment a build version injected into HTML, and set dev cache headers (`no-store`) in `--watch` mode.
5. **`record-editor.js` / 900-line `renderRecord()`** — Problem: deferring all decomposition leaves the highest-risk area unchanged, so blast radius remains large even after modularization. Suggested fix: keep full function split out of scope, but require a minimum seam now: extract pure sub-render helpers and event-binding blocks into adjacent files or internal helpers, with zero behavior change.
6. **Risks & Mitigations table (missing failure modes)** — Problem: plan misses syntax/bundle-break detection before runtime and export-path regressions. Suggested fix: add explicit CI/dev checks: concatenate + parse check (at minimum browser-run smoke), static-export open test, and “all placeholders resolved” assertion.

## Secondary issues
1. **Why not `<script src=>` section** — Problem: it treats `src` mode as all-or-nothing; dev and export needs are different. Suggested fix: consider split strategy: multi-file `script src` in `--serve --watch` for easier debugging, concatenated single blob only for export/deploy.
2. **CSS ordering note (`tokens first, then any order`)** — Problem: CSS order is not arbitrary once selectors overlap; later files can unintentionally override layout rules. Suggested fix: define explicit CSS load order and enforce it in one manifest next to the template sources.
3. **Phase 0** — Problem: command alias is useful but not on the critical path of architecture risk reduction. Suggested fix: either fold it into Phase 1 as a quick task or postpone until after concat parity is proven.
4. **Ownership of module boundaries** — Problem: no rule for allowed cross-module access means globals can sprawl again. Suggested fix: document a minimal contract (what each module may read/write) and reject new undeclared globals.

## Checks passed
- The plan directly addresses the main problem (monolith to modular sources) without changing deployment artifact shape.
- Constraints are mostly realistic: no Node toolchain, Fly.io single-file output, Python-owned build path, and serve/export dual consumers.
- Scope is appropriately bounded for Phase 1 (no framework/TS rewrite).
- Incremental extraction sequence is sensible at a high level and likely executable by a small team.
